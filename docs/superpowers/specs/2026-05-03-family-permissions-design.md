# Fawn 家庭组与权限管理设计规格

| 字段 | 值 |
|------|-----|
| 版本 | v1.0 |
| 日期 | 2026-05-03 |
| 状态 | review-ready |
| 依赖 | `docs/PRD-V2.md`, 当前 `/profile`, `/chat`, `/album`, tracker 权限实现 |

---

## 1. 目标

将 Fawn 的“家庭”Tab 从个人资料与简单权限页升级为家庭设置中心，并把产品底座明确为：

- 一个家庭是一个独立数据边界。
- 一个账号只属于一个家庭。
- 一个家庭共享一个连续聊天窗口。
- 管家能够识别当前发言人的家庭角色和权限类型。

本设计解决当前实现与产品定位不一致的问题：现有聊天、画像和部分数据查询以 `user_id` 为主，真实效果更像每个账号私聊；目标是家庭成员共同使用同一个家庭空间。

---

## 2. 当前问题

### 2.1 权限模型过窄

当前用户模型主要依赖：

- `role = admin | parent | family`
- `permissions.can_upload_photos`
- `permissions.can_write_tracker`

这无法表达“权限类型”和“家庭角色”的区别。例如“儿科医生”可能是 `friend` 权限类型，但聊天 UI 应显示角色“儿科医生”，而不是显示“朋友”。

### 2.2 缺少家庭数据边界

当前主要数据归属分散在 `user_id` 或 `baby_id` 上，没有统一的 `family_id`：

- `users` 没有家庭归属。
- `babies` 没有家庭归属。
- tracker records 主要挂 `baby_id`。
- photos 主要挂 `baby_id`。
- conversations 只挂 `user_id`。
- profile items 只挂 `user_id`。

这会阻碍未来多家庭隔离，也让当前“家庭共享”的语义不稳定。

### 2.3 聊天不是家庭群聊

当前 `Conversation` 按 `user_id` 归属，列表、搜索、读取、图片访问都要求当前用户拥有该 conversation。产品目标应改为：家庭共享一个连续聊天流，所有家庭成员可以看到同一份聊天记录。

---

## 3. 核心决策

### 3.1 家庭组

新增 `families` 作为 tenant 边界。第一版只显示和使用当前默认家庭，不实现多家庭切换。

一个账号只属于一个家庭。如果同一个真人在另一个家庭中也有身份，应创建另一个账号。这样可以避免多对多 membership 和跨家庭身份切换复杂度。

### 3.2 成员字段

用户账号新增两个核心字段：

| 字段 | 类型 | 用途 |
|------|------|------|
| `access_type` | `parent | family | friend` | 授权判断 |
| `role` | 自由文本 | UI 展示和管家上下文 |

`access_type` 决定能做什么，`role` 不参与权限判断。

示例：

| display_name | access_type | role |
|--------------|-------------|------|
| 爸爸 | parent | 爸爸 |
| 奶奶 | family | 奶奶 |
| 李医生 | friend | 儿科医生 |
| 小王 | friend | 同事 |

### 3.3 旧字段迁移

旧 `role` 字段应迁移为新 `access_type`：

| 旧 role | 新 access_type |
|---------|-----------------|
| `admin` | `parent` |
| `parent` | `parent` |
| `family` | `family` |

旧 `permissions` 不再作为主要授权来源。第一版可以保留字段用于兼容，但新业务判断应集中到 `access_type`。

---

## 4. 数据模型

### 4.1 Families

新增 `families` 表：

| 字段 | 说明 |
|------|------|
| `id` | 家庭 ID |
| `name` | 家庭名称，例如“晨晨的家庭” |
| `created_at` / `updated_at` | 时间戳 |

### 4.2 Users

`users` 增加：

| 字段 | 说明 |
|------|------|
| `family_id` | 账号所属家庭 |
| `access_type` | `parent | family | friend` |
| `role` | 自由文本家庭角色 |

`username` 仍可全局唯一。第一版不做同一个账号跨家庭登录。

### 4.3 Baby Profiles

`babies` 增加 `family_id`。第一版仍可以假设一个家庭一个宝宝，但数据结构不应阻止以后一个家庭多个宝宝档案。

### 4.4 Records And Photos

所有家庭共享数据必须可按 `family_id` 隔离：

- growth records
- feeding records
- sleep records
- health records
- photos
- photo tags 通过 photos 间接归属家庭

查询规则：用户只能读取自己 `family_id` 下的数据。

### 4.5 Chat Stream

产品上不再暴露 conversation/session。目标模型：

- 家庭有一条连续聊天流。
- 每条消息属于一个 `family_id`。
- 用户消息记录 `sender_user_id`。
- 管家消息没有普通 sender，或使用明确的 assistant 标记。

可选实现方式：

- 复用 `conversations` 作为内部家庭聊天容器，但不在 UI 暴露 session。
- 或新增 `chat_messages` / `chat_summaries`，逐步替代用户可见 conversation。

无论实现路径如何，API 语义应面向家庭聊天流，而不是用户私聊。

### 4.6 Memory And Profile

记忆分为两类：

| scope | 归属 | 用途 |
|-------|------|------|
| `family` | `family_id` | 宝宝和家庭层面的长期事实 |
| `user` | `user_id` | 当前发言人的个人偏好和画像 |

管家 prompt 同时使用家庭记忆和当前发言人的个人画像。

---

## 5. 权限矩阵

### 5.1 Parent

父母拥有最高权限：

- 查看所有家庭数据。
- 新增、编辑、软删除普通记录。
- 上传、下载、软删除照片。
- 创建账号、删除账号、修改账号密码。
- 修改成员 `access_type` 和 `role`。
- 修改宝宝档案和家庭名称。
- 管理家庭记忆。
- 和管家聊天，并允许管家工具写入数据。

### 5.2 Family

家人拥有日常照护权限：

- 查看所有家庭数据。
- 新增、编辑、软删除普通记录。
- 上传、下载、软删除照片。
- 和管家聊天，并允许管家工具写入数据。

家人不能：

- 创建或删除账号。
- 修改账号密码。
- 修改成员权限。
- 修改家庭名称。

### 5.3 Friend

朋友是只读参与者：

- 查看 Dashboard、记录、相册、宝宝档案和聊天记录。
- 下载照片。
- 和管家聊天。

朋友不能：

- 新增、编辑、删除或软删除任何数据。
- 上传或软删除照片。
- 通过管家工具写入数据。
- 管理账号、权限或家庭设置。

### 5.4 后端强制

权限不能只依赖前端隐藏按钮。所有写入 API 和 Agent tools 都必须在后端根据 `access_type` 拦截。

对于 `friend`，即使在聊天中请求“帮我记录”，工具层也必须拒绝写入，并让管家用自然语言说明当前账号只有查看和聊天权限。

## 6. 共享聊天设计

### 6.1 产品行为

聊天页是家庭共享空间：

- 所有家庭成员进入聊天页看到同一条家庭消息流。
- 没有用户可见的“新建会话”或“历史会话”概念。
- 历史按时间连续呈现，可按日期分组。
- 搜索范围是当前家庭的共享聊天记录。

### 6.2 消息展示

用户消息展示当前发言人的：

- `display_name`
- `role`
- 头像

普通聊天 UI 不强调 `access_type`。例如 `access_type=friend`, `role=儿科医生` 的成员，消息旁显示“儿科医生”，不是“朋友”。

家庭设置页可以显示 `access_type`，帮助父母理解权限。

### 6.3 Prompt Context

每次管家回复时，应包含：

- 当前发言人姓名。
- 当前发言人的 `role`。
- 当前发言人的 `access_type`。
- 宝宝档案。
- 家庭记忆。
- 当前发言人的个人画像。
- 最近聊天上下文或摘要。

### 6.4 内部摘要

虽然产品上是一条连续聊天流，后端仍可以做内部摘要切片以控制上下文长度。摘要切片不应作为用户可见 session。

---

## 7. 家庭设置页 UI

底部 Tab 仍为“家庭”，路由可继续使用 `/profile`，但页面语义升级为家庭设置中心。

采用单页滚动结构。

### 7.1 顶部家庭概览

显示：

- 家庭名称。
- 当前登录者头像、昵称、角色。
- 当前权限类型的轻量说明，例如“爸爸 · 父母权限”。

### 7.2 宝宝档案

显示：

- 姓名、性别、出生日期、年龄。
- 出生体重、身高、头围。
- 是否早产和孕周。

`parent` 可编辑；`family` 和 `friend` 只读。

### 7.3 家庭成员

显示所有成员：

- 头像。
- 昵称。
- 自由文本 `role`。
- `access_type` 标签。

`parent` 可以：

- 创建账号。
- 删除账号。
- 修改密码。
- 修改成员昵称、角色和权限类型。

非 `parent` 只读。

### 7.4 权限说明

用简洁矩阵或说明卡解释：

- 父母。
- 家人。
- 朋友。

这部分不要抢占首屏，应作为帮助父母理解权限的轻量说明。

### 7.5 家庭记忆

展示家庭共享记忆。第一版建议只允许 `parent` 管理，避免普通成员误删家庭级上下文。

### 7.6 我的画像

展示当前账号的个人画像。当前账号可以编辑和删除自己的画像条目。

## 8. API 方向

### 8.1 Auth / Users

需要支持：

- 获取当前用户及其家庭信息。
- 列出当前家庭成员。
- 父母创建成员账号。
- 父母删除成员账号。
- 父母修改成员密码。
- 父母修改成员 `access_type` 和 `role`。

### 8.2 Family

需要支持：

- 获取当前家庭。
- 父母更新家庭名称。

### 8.3 Chat

需要支持家庭共享聊天：

- 获取当前家庭聊天消息流。
- 发送消息到当前家庭聊天。
- 搜索当前家庭聊天。
- 上传和读取聊天图片时按家庭授权。

旧 conversation API 可以保留兼容层，但新前端应逐步切到家庭聊天语义。

### 8.4 Tracker / Album / Dashboard

所有读取和写入都应隐式使用当前用户的 `family_id` 作为边界。客户端不应能够通过传入别的 `family_id` 越权读取。

---

## 9. 迁移策略

### 9.1 创建默认家庭

迁移时创建一个默认家庭，例如“晨晨的家庭”或根据现有宝宝名生成家庭名。

### 9.2 绑定现有数据

将现有数据绑定到默认家庭：

- 所有用户设置 `family_id`。
- 所有宝宝设置 `family_id`。
- 所有记录根据 `baby_id` 对应到家庭。
- 所有照片根据 `baby_id` 对应到家庭。
- 所有聊天数据迁入默认家庭聊天范围。
- 所有 profile items 默认保留为 `user` scope；后续可通过自动抽取或手动整理形成 `family` scope。

### 9.3 迁移旧权限

将旧 role 映射到 `access_type`：

- `admin` 和 `parent` 变成 `parent`。
- `family` 变成 `family`。

旧 `permissions` 保留一段时间以降低风险，但新权限判断应优先使用 `access_type`。

## 10. 测试要求

### 10.1 后端

覆盖：

- `parent` 能创建、删除账号、改密码、改权限。
- `family` 不能管理账号。
- `friend` 不能写 tracker、上传照片、软删除数据。
- `friend` 可以读取 Dashboard、记录、相册、聊天，并下载照片。
- 所有数据读取都按 `family_id` 限制。
- 管家工具对 `friend` 写入请求返回权限拒绝。
- 旧数据迁移后仍能读取。

### 10.2 前端

覆盖：

- 家庭设置页按 `access_type` 展示不同操作。
- 聊天消息展示 `role`，不把权限类型当作聊天身份。
- friend 看不到写入入口、上传入口、删除入口。
- parent 能看到账号管理入口。
- shared chat 加载同一家庭消息流。

### 10.3 手工验证

至少用三个账号验证：

- 爸爸：`access_type=parent`, `role=爸爸`
- 奶奶：`access_type=family`, `role=奶奶`
- 医生：`access_type=friend`, `role=儿科医生`

验证三者看到同一个聊天流，且医生无法写入数据。

---

## 11. 非目标

第一版不做：

- 多家庭切换 UI。
- 一个账号加入多个家庭。
- 邀请链接和注册流程。
- 权限模板。
- 细分到“只看健康数据”“只看相册”的字段级权限。
- 永久删除数据的完整回收站 UI。

这些能力可以在家庭组边界稳定后继续扩展。

---

## 12. 风险与约束

- 聊天从用户私聊改为家庭共享，影响面较大，应优先写后端回归测试。
- `Conversation` 是否复用为内部上下文窗口，需要在实现计划中进一步拆解，避免一次性迁移过大。
- 旧 `permissions` 与新 `access_type` 共存期间必须明确优先级，避免前后端判断不一致。
- 家庭记忆自动抽取需要保守，避免把个人偏好误写成家庭事实。
- 软删除普通数据的范围要逐个资源落实；当前相册已支持软删除，但 tracker 记录仍需要统一设计。

---

## 13. 推荐实施顺序

1. 新增家庭组与用户 `access_type` / `role` 数据模型，完成迁移。
2. 将读取 API 按 `family_id` 隔离，保留当前 UI 行为。
3. 改造权限 helpers 和后端依赖，统一使用 `access_type`。
4. 改造家庭设置页为单页滚动中心。
5. 改造聊天为家庭共享消息流，并加入 `sender_user_id`。
6. 接入家庭记忆和个人画像双 scope。
7. 补齐 friend 只读、family 日常写入、parent 管理账号的测试。
