## 1. 执行摘要

本文档为宝宝专属 Agent 设计一套 **6 层知识架构**（L1–L6），覆盖从硬编码医学规则到用户个性化记忆的完整知识谱系。核心设计原则：

- **安全优先**：所有涉及医疗判断的知识走 deterministic rules，LLM 仅负责自然语言包装，不做最终医学决策。
- **隐私保守**：儿童数据严格分级，最小化存储、最小化暴露、全链路审计。
- **可检索、可更新、可审计**：每层知识都有明确的写入路径、检索接口和版本控制策略。
- **支撑下游**：层级划分直接映射到 D1 的数据库 schema 分区、E1 的测试用例分类、F1 的合规检查点、G1 的里程碑排期。

**推荐结论**：采用 6 层分离架构，L1/L2 为 deterministic 层（规则引擎 + 结构化医学知识），L3/L4 为 RAG 辅助层（育儿百科 + 社区经验），L5/L6 为个性化层（家庭档案 + 对话记忆）。检索路由采用 "规则优先、向量兜底" 的级联策略。

## 2. 设计目标与原则

### 2.1 设计目标

| # | 目标 | 衡量标准 |
|---|------|---------|
| G1 | 红旗症状零漏判 | L1 规则覆盖率 ≥ 99%，recall ≥ 99.5% |
| G2 | 疫苗提醒准确 | 与 NIP 官方日历 100% 一致 |
| G3 | 育儿问答有据可查 | 每条回复可追溯至具体知识层+来源 |
| G4 | 个性化记忆连贯 | 跨会话记忆召回准确率 ≥ 95% |
| G5 | 隐私合规 | 满足《个人信息保护法》《儿童个人信息网络保护规定》 |
| G6 | 多成员协作 | 家庭成员权限隔离，操作可审计 |

### 2.2 核心原则

1. **Deterministic First**：凡是有明确医学/法规依据的判断，必须走规则引擎，不走 LLM。
2. **知识分级**：按可信度、时效性、风险等级分层存储与检索。
3. **来源可溯**：每条知识附带来源元数据（出处、版本、审核状态、许可证）。
4. **最小存储**：个人数据仅存必要字段，定期清理过期记忆。
5. **权限分层**：不同知识层有不同的读写权限矩阵。
6. **更新可控**：医学知识更新需人工审核，不允许 LLM 自主修改规则。

## 3. 推荐的 6 层知识架构

```
┌─────────────────────────────────────────────────────────┐
│                    检索路由器 (Query Router)               │
│         意图分类 → 层级选择 → 级联查询 → 结果融合           │
└────────┬──────────┬──────────┬──────────┬──────────┬─────┘
         │          │          │          │          │
    ┌────▼───┐ ┌───▼────┐ ┌──▼───┐ ┌───▼───┐ ┌───▼───┐ ┌───────┐
    │  L1    │ │  L2    │ │  L3  │ │  L4   │ │  L5   │ │  L6   │
    │硬编码  │ │结构化  │ │育儿  │ │经验   │ │家庭   │ │对话   │
    │医学    │ │医学    │ │百科  │ │知识   │ │档案   │ │记忆   │
    │规则    │ │知识库  │ │文档  │ │       │ │       │ │       │
    └────────┘ └────────┘ └──────┘ └───────┘ └───────┘ └───────┘
    ◄─── Deterministic ──►◄──── RAG 辅助 ────►◄── 个性化 ──►
    ◄───── 高可信度 ──────►◄──── 中可信度 ────►◄── 私有 ───►
```

### 3.1 层级总览

| 层级 | 名称 | 性质 | 可信度 | 决策权 | 存储引擎 | 数据规模 |
|------|------|------|--------|--------|----------|----------|
| L1 | 硬编码医学规则 | Deterministic | ★★★★★ | **否决权** | 代码/配置文件 | ~500 条规则 |
| L2 | 结构化医学知识库 | Deterministic + 查表 | ★★★★★ | 高优先 | PostgreSQL | ~10K 条目 |
| L3 | 育儿百科文档 | RAG 检索 | ★★★★☆ | 参考级 | 向量数据库 + 原文 | ~50K 文档块 |
| L4 | 经验知识 | RAG 检索 | ★★★☆☆ | 辅助级 | 向量数据库 | ~100K 文档块 |
| L5 | 家庭档案 | 个性化存储 | ★★★★★（事实）| 上下文级 | PostgreSQL | 按家庭增长 |
| L6 | 对话记忆 | 短期+长期记忆 | ★★★☆☆ | 上下文级 | Redis + PostgreSQL | 按会话增长 |

## 4. 每层详细设计

### 4.1 L1：硬编码医学规则

#### 存什么

| 子类 | 示例 | 条目量 |
|------|------|--------|
| 红旗症状规则 | 新生儿体温 ≥ 38°C → 立即就医 | ~200 条 |
| 年龄适宜性规则 | < 1 岁禁食蜂蜜 | ~100 条 |
| 剂量/喂养上限 | 对乙酰氨基酚 10–15mg/kg/次 | ~80 条 |
| 紧急处置流程 | 异物窒息 → 海姆立克法指导 | ~50 条 |
| 安全否决规则 | 任何建议不得替代就医 | ~20 条 |
| 疫苗绝对禁忌 | 严重过敏反应后禁止同种疫苗 | ~50 条 |

#### 为什么单独一层

- **零容忍误判**：红旗症状漏判可能危及生命，必须 100% 确定性执行。
- **审计可追溯**：规则变更走代码 PR 审核 + 医学顾问签字。
- **不依赖 LLM**：即使 LLM 服务宕机，规则引擎仍可独立运行。

#### 怎么检索

```
输入：symptoms[], age_months, weight_kg, context
  ↓
规则引擎（Rete 算法 / 决策树）
  ↓
输出：{matched_rules[], severity, action, explanation_template}
```

- 检索方式：**精确匹配 + 条件求值**，无模糊搜索。
- 延迟要求：< 10ms（P99）。
- 主 Agent 收到 L1 结果后**必须执行**，不得覆盖。

#### 怎么更新

| 步骤 | 负责人 | 说明 |
|------|--------|------|
| 1. 提出变更 | 开发/运营 | 提交 PR，附医学来源引用 |
| 2. 医学审核 | 签约医学顾问 | 审核规则正确性、边界条件 |
| 3. 代码审核 | 技术负责人 | 审核实现正确性 |
| 4. 回归测试 | CI/CD | E1 eval harness 全量回归 |
| 5. 灰度发布 | SRE | 1% → 10% → 100% |

- **更新频率**：按需，预计每季度 1–2 次。
- **禁止热更新**：不允许运行时动态修改规则。

#### 权限与风险

| 角色 | 读 | 写 | 风险 |
|------|:--:|:--:|------|
| 规则引擎 | ✅ | ❌ | — |
| 主 Agent | ✅（结果）| ❌ | 不得绕过规则 |
| 医学顾问 | ✅ | 提案 | 需双人审核 |
| 开发者 | ✅ | PR | 必须附来源 |
| 用户 | ❌（仅看结果）| ❌ | — |

**风险**：规则遗漏（未覆盖的罕见症状）。缓解：L1 兜底规则 "无法判断时建议就医"。

### 4.2 L2：结构化医学知识库

#### 存什么

| 子类 | 示例 | 格式 |
|------|------|------|
| 疫苗日历 | NIP 免疫程序表（2025版）| 结构化表 |
| 生长曲线 | WHO 0–5 岁身高/体重/头围百分位 | 数值表 |
| 月龄里程碑 | 大运动/精细运动/语言/社交发展 | 结构化清单 |
| 辅食引入时间表 | 各月龄推荐/禁忌食材 | 结构化表 |
| 常见疾病知识卡 | 手足口病：症状、病程、护理、就医指征 | 半结构化 JSON |
| 药物安全参考 | 儿童常用药剂量、禁忌、相互作用 | 结构化表 |

#### 为什么单独一层

- 与 L1 的区别：L1 是"判断规则"（if-then），L2 是"参考数据"（查表取值）。
- 结构化存储使得**精确查询成为可能**（如：查 3 月龄疫苗 → 精确返回"百白破第1剂"）。
- 支撑 Temporal workflow（疫苗提醒需要精确日期计算）。

#### 怎么检索

```sql
-- 示例：查询 3 月龄应接种的疫苗
SELECT vaccine_name, dose_number, earliest_date, latest_date
FROM vaccine_schedule
WHERE age_months = 3 AND program = 'NIP_2025';
```

- 检索方式：**SQL 精确查询**，支持参数化。
- 延迟要求：< 20ms（P99）。
- 支持**联合查询**：结合 L5 家庭档案中宝宝的实际出生日期计算具体接种日。

#### 怎么更新

| 来源 | 更新方式 | 频率 | 审核 |
|------|---------|------|------|
| WHO 生长标准 | 批量导入 | 极少（标准修订时）| 医学顾问 |
| NIP 疫苗日历 | 人工录入 | 年度 | 医学顾问 + 交叉验证 |
| 疾病知识卡 | 人工编写 | 按需 | 医学顾问 |
| 药物参考 | 批量导入 + 人工校对 | 半年度 | 药学顾问 |

- **版本控制**：所有更新保留历史版本，支持回滚。
- **生效控制**：新版本需通过 E1 回归测试后方可上线。

#### 权限与风险

| 角色 | 读 | 写 | 风险 |
|------|:--:|:--:|------|
| 主 Agent | ✅ | ❌ | — |
| 规则引擎 | ✅ | ❌ | 联合 L1 判断 |
| Temporal 工作流 | ✅ | ❌ | 疫苗日期计算 |
| 医学顾问 | ✅ | ✅（审核后）| 数据录入错误 |
| 用户 | ❌（仅看格式化结果）| ❌ | — |

**风险**：数据滞后（疫苗政策调整后未及时更新）。缓解：设置定期巡检任务 + 版本有效期。

### 4.3 L3：育儿百科文档

#### 存什么

| 子类 | 示例来源 | 说明 |
|------|---------|------|
| 权威指南摘要 | AAP、WHO、中国CDC 育儿指南 | 需获取版权许可或仅引用公开摘要 |
| 自建育儿百科 | 自有团队编写 | 覆盖常见问题 Q&A |
| 睡眠训练方法 | 经整理的各流派方法论 | 明确标注"非医学建议" |
| 辅食食谱库 | 按月龄分类的食谱 | 标注过敏原 |
| 发育引导活动 | 按月龄的亲子游戏/早教活动 | 安全提示 |

#### 为什么单独一层

- 与 L2 的区别：L2 是"精确可查表的结构化事实"，L3 是"需要语义检索的非结构化文档"。
- 是 RAG 的主要知识源，直接影响日常问答质量。
- 版权与许可管理需要独立处理。

#### 怎么检索

```
用户问题 → Query 改写 → Embedding → 向量搜索（Top-K）
                                         ↓
                                    重排序 (Reranker)
                                         ↓
                                    摘要 + 引用拼接
                                         ↓
                                    LLM 生成回复
```

- 检索方式：**向量相似度检索 + BM25 混合检索**。
- 向量数据库选型：Qdrant / pgvector（与 L2 共用 PostgreSQL 实例降低运维成本）。
- Chunk 策略：按段落 + 语义边界切分，chunk_size = 512 tokens，overlap = 64 tokens。
- 延迟要求：< 200ms（P95）。
- 必须返回**来源引用**（文档名、章节、原文片段）。

#### 怎么更新

| 操作 | 方式 | 频率 |
|------|------|------|
| 新增文档 | 编辑审核 → 切片 → Embedding → 入库 | 按需 |
| 修改文档 | 旧 chunk 标记废弃 → 新 chunk 入库 | 按需 |
| 删除文档 | 软删除 → 从索引移除 | 按需 |
| 全量重建 | Embedding 模型升级时 | 预计每年 1–2 次 |

- **质量控制**：新文档入库前需经过编辑审核，确保与 L1/L2 不冲突。

#### 权限与风险

| 角色 | 读 | 写 | 风险 |
|------|:--:|:--:|------|
| 主 Agent（RAG）| ✅ | ❌ | 检索不准导致回答偏差 |
| 内容编辑 | ✅ | ✅ | 内容质量把控 |
| 用户 | ❌（仅看 LLM 综合后的回复）| ❌ | — |

**风险**：
1. **幻觉风险**：LLM 可能在 RAG 结果基础上产生不准确的扩展。缓解：强制引用来源、safety_gate 检查。
2. **版权风险**：引用第三方内容。缓解：见 §7 版权边界。

### 4.4 L4：经验知识

#### 存什么

| 子类 | 示例 | 可信度 |
|------|------|--------|
| 常见问题模板回复 | "宝宝吐奶正常吗？" 的标准回复模板 | ★★★★☆ |
| 场景化 few-shot 示例 | 高质量对话示例（prompt engineering 用）| ★★★★☆ |
| 产品使用指南 | 如何记录喂养、如何查看生长曲线 | ★★★★★ |
| 育儿经验帖（精选）| 经审核的用户经验分享 | ★★★☆☆ |
| 地域化知识 | 各地疫苗接种点、母婴政策差异 | ★★★☆☆ |

#### 为什么单独一层

- 与 L3 的区别：L3 是"权威知识"，L4 是"经验/运营知识"，可信度更低，更新更频繁。
- 分离后可独立控制 L4 的检索权重（降权处理）。
- 包含 prompt engineering 相关资源（few-shot 示例），与纯知识内容性质不同。

#### 怎么检索

- 与 L3 共用向量检索管道，但通过 **metadata 标签** 区分层级。
- 检索时可通过 `layer=L4` 过滤，或在混合检索中给 L4 结果降权（权重系数 0.6–0.8）。
- Few-shot 示例走**精确匹配**（按意图分类索引），不走向量检索。

#### 怎么更新

| 操作 | 频率 | 审核级别 |
|------|------|---------|
| 新增模板回复 | 每周 | 运营审核 |
| 更新 few-shot | 每月 | 技术 + 运营联合审核 |
| 精选用户经验 | 每周 | 内容审核（去个人信息）|
| 地域化数据 | 按需 | 运营审核 |

#### 权限与风险

| 角色 | 读 | 写 | 风险 |
|------|:--:|:--:|------|
| 主 Agent（RAG）| ✅ | ❌ | 低可信度内容被过度依赖 |
| 运营 | ✅ | ✅ | 内容质量参差 |
| 用户 | ❌（间接）| 投稿（需审核）| 隐私泄露 |

**风险**：用户经验帖可能包含个人信息或错误医学建议。缓解：严格脱敏 + 医学内容标注"非专业建议"。

### 4.5 L5：家庭档案

#### 存什么

| 子类 | 字段示例 | 敏感级别 |
|------|---------|---------|
| 宝宝基本信息 | 姓名、出生日期、性别、血型 | 🔴 高 |
| 生长记录 | 身高、体重、头围 + 测量日期 | 🟡 中 |
| 喂养记录 | 母乳/配方奶/辅食，每日明细 | 🟡 中 |
| 睡眠记录 | 入睡时间、醒来时间、小睡次数 | 🟢 低 |
| 疫苗接种记录 | 已接种疫苗、日期、批号、反应 | 🔴 高 |
| 过敏/疾病史 | 已知过敏原、既往疾病 | 🔴 高 |
| 家庭成员 | 家长/祖辈/保姆，角色、权限 | 🔴 高 |
| 用户偏好 | 语言风格、提醒频率、关注重点 | 🟢 低 |

#### 为什么单独一层

- 这是**用户私有数据**，与公共知识（L1–L4）性质完全不同。
- 是个性化回复的核心依据（如根据宝宝月龄过滤食材建议）。
- 隐私合规的主要管控对象。

#### 怎么检索

```sql
-- 示例：获取当前宝宝的疫苗接种状态
SELECT v.vaccine_name, v.dose_number, vr.vaccinated_date, vr.reaction
FROM vaccine_schedule v
LEFT JOIN vaccination_records vr
  ON v.vaccine_id = vr.vaccine_id AND vr.baby_id = :baby_id
WHERE v.age_months <= :current_age_months;
```

- 检索方式：**SQL 精确查询**，必须带 `family_id` / `baby_id` 作为查询条件。
- **禁止全表扫描**：所有查询必须限定到当前授权家庭。
- 延迟要求：< 30ms（P99）。

#### 怎么更新

| 操作 | 触发方式 | 验证 |
|------|---------|------|
| 记录喂养/睡眠 | 用户输入（自然语言/表单）| 格式校验 + 合理性检查 |
| 更新生长数据 | 用户输入 | 范围校验（WHO 曲线 ±4SD 告警）|
| 记录疫苗接种 | 用户输入 | 与 L2 疫苗日历交叉验证 |
| 添加家庭成员 | 家庭管理员操作 | 邀请确认机制 |

- **合理性检查**：异常值（如体重突变 ≥ 2kg/周）触发提示但不阻止录入。
- **数据导出**：支持用户导出自己的全部数据（GDPR/PIPL 要求）。

#### 权限与风险

| 角色 | 读 | 写 | 特殊限制 |
|------|:--:|:--:|---------|
| 主 Agent | ✅（当前家庭）| ✅（经用户确认）| 不得跨家庭访问 |
| 家庭管理员（家长）| ✅ 全部 | ✅ 全部 | 可管理成员权限 |
| 协助看护人（祖辈/保姆）| ✅ 日常记录 | ✅ 日常记录 | 不可修改基本信息 |
| 只读成员 | ✅ 日常记录 | ❌ | — |
| LLM | ❌ 直接访问 | ❌ | 仅通过 Tool 接口获取 |

**风险**：
1. **数据泄露**：个人信息暴露。缓解：加密存储、TLS 传输、最小权限。
2. **数据篡改**：恶意修改接种记录。缓解：操作审计日志、关键操作二次确认。
3. **跨家庭泄露**：Agent 混淆不同家庭数据。缓解：查询层强制 family_id 过滤、E1 测试覆盖。

---

### 4.6 L6：对话记忆

#### 存什么

| 子类 | 存储位置 | 保留策略 |
|------|---------|---------|
| 当前会话上下文 | Redis（内存）| 会话结束后 24h 过期 |
| 会话摘要 | PostgreSQL | 保留 90 天 |
| 长期偏好提取 | PostgreSQL（L5 偏好字段）| 长期保留 |
| 重要事件标记 | PostgreSQL | 长期保留 |

#### 为什么单独一层

- 与 L5 的区别：L5 是"结构化事实记录"，L6 是"非结构化对话衍生信息"。
- 记忆管理策略（遗忘、压缩、提取）需要独立的生命周期管理。
- 是实现"连贯对话体验"的关键层，但不应影响医学判断。

#### 怎么检索

```
当前用户输入
     ↓
  ┌──────────────────────┐
  │  1. 取当前会话上下文   │ ← Redis，最近 N 轮
  │  2. 取最近会话摘要     │ ← PostgreSQL，最近 K 条
  │  3. 取长期偏好         │ ← L5 偏好字段
  └──────────────────────┘
     ↓
  拼接为 LLM context window
```

- 短期记忆：最近 10 轮对话，直接拼入 prompt。
- 中期记忆：最近 7 天的会话摘要，按相关性选取。
- 长期记忆：提取为结构化偏好，合并入 L5。

#### 怎么更新

| 操作 | 触发时机 | 方式 |
|------|---------|------|
| 追加当前轮 | 每轮对话 | 写入 Redis |
| 生成会话摘要 | 会话结束 | LLM 摘要 → PostgreSQL |
| 提取长期偏好 | 会话结束 | LLM 提取 → 写入 L5 |
| 清理过期记忆 | 定时任务 | 按保留策略清理 |

- **摘要质量控制**：摘要不得包含医学诊断结论（仅记录"用户曾询问过 X"）。

#### 权限与风险

| 角色 | 读 | 写 | 风险 |
|------|:--:|:--:|------|
| 主 Agent | ✅（当前用户会话）| ✅ | 记忆污染 |
| 用户 | ✅（可查看历史）| ✅（可删除）| — |
| 其他家庭成员 | ❌ | ❌ | 隐私隔离 |

**风险**：
1. **记忆污染**：错误信息进入长期记忆。缓解：长期偏好提取需置信度阈值。
2. **隐私**：对话中可能包含敏感信息。缓解：摘要自动脱敏、PII 检测。

## 5. Deterministic Rules vs LLM 分工

### 5.1 分工矩阵

```
            高风险                    低风险
         ┌──────────────────┬──────────────────┐
高确定性  │  L1: 规则引擎     │  L2: 查表计算    │
         │  红旗症状判断      │  疫苗日期计算    │
         │  药物禁忌检查      │  生长曲线百分位  │
         │  ⚙️ Deterministic │  ⚙️ Deterministic│
         ├──────────────────┼──────────────────┤
低确定性  │  L1兜底→就医建议  │  L3/L4: RAG+LLM │
         │  不确定时保守处理   │  育儿问答       │
         │  ⚙️ Deterministic │  🤖 LLM + 引用   │
         │  (fail-safe)     │  + safety_gate   │
         └──────────────────┴──────────────────┘
```

### 5.2 详细分工表

| 功能场景 | 处理方式 | 知识层 | 说明 |
|---------|---------|--------|------|
| 红旗症状识别 | **Deterministic** | L1 | LLM 仅格式化输出文案 |
| 疫苗到期提醒 | **Deterministic** | L2 + L5 | Temporal 调度 + 精确计算 |
| 生长曲线评估 | **Deterministic** | L2 + L5 | 百分位计算为数学运算 |
| 喂养/睡眠趋势分析 | **Deterministic 计算 + LLM 解读** | L5 | 统计计算确定性，自然语言解读用 LLM |
| 辅食推荐 | **Deterministic 过滤 + LLM 组织** | L1(禁忌) + L2(月龄) + L3(食谱) | 先用规则排除禁忌，再用 LLM 组织推荐 |
| 育儿问答 | **LLM + RAG** | L3 + L4 | safety_gate 最终检查 |
| 睡眠训练建议 | **LLM + RAG** | L3 + L4 | 标注"非医学建议" |
| 症状问诊引导 | **Deterministic 主导 + LLM 对话** | L1 + L3 | 结构化问诊流程，LLM 做自然语言交互 |
| 对话记忆管理 | **LLM** | L6 | 摘要生成、偏好提取 |
| 权限管理 | **Deterministic** | L5 | 纯逻辑判断 |

### 5.3 safety_gate 在知识层间的作用

```
L3/L4 RAG 结果 + LLM 生成的回复
              ↓
         safety_gate
              ↓
    ┌─────────────────────────┐
    │ 1. 是否触发 L1 红旗规则？  │ → 是 → 覆盖回复为就医建议
    │ 2. 是否包含禁忌建议？      │ → 是 → 拦截 + 告警
    │ 3. 是否超出能力边界？      │ → 是 → 引导就医
    │ 4. 是否包含未经审核的医学  │
    │    诊断/处方？             │ → 是 → 拦截
    └─────────────────────────┘
              ↓
         输出给用户
```

## 6. 检索与路由流程

### 6.1 完整检索路由 ASCII 图

```
┌─────────────────────────────────────────────────────────────┐
│                      用户输入 (Query)                        │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌──────────────────────────▼──────────────────────────────────┐
│              意图分类 (Intent Classifier)                     │
│  输入: query + L6 会话上下文 + L5 宝宝月龄                     │
│  输出: intent_type, urgency_level, required_layers[]         │
│  方式: 轻量分类模型 or LLM function calling                   │
└──┬──────────┬──────────┬──────────┬──────────┬──────────┬───┘
   │          │          │          │          │          │
   ↓          ↓          ↓          ↓          ↓          ↓
┌──▼──┐  ┌───▼──┐  ┌───▼──┐  ┌───▼──┐  ┌───▼──┐  ┌───▼──┐
│ L1  │  │  L2  │  │  L3  │  │  L4  │  │  L5  │  │  L6  │
│规则  │  │查表  │  │ RAG  │  │ RAG  │  │档案  │  │记忆  │
│引擎  │  │查询  │  │检索  │  │检索  │  │查询  │  │召回  │
└──┬──┘  └───┬──┘  └───┬──┘  └───┬──┘  └───┬──┘  └───┬──┘
   │          │          │          │          │          │
   ↓          ↓          ↓          ↓          ↓          ↓
┌──▼──────────▼──────────▼──────────▼──────────▼──────────▼──┐
│                    结果融合器 (Result Merger)                 │
│  1. L1 结果有否决权 → 如触发红旗，覆盖一切                     │
│  2. L2 精确结果优先级高于 L3/L4 RAG 结果                      │
│  3. L3/L4 结果按可信度加权排序                                │
│  4. L5 个性化信息用于上下文增强                                │
│  5. L6 记忆用于连贯性维护                                     │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌──────────────────────────▼──────────────────────────────────┐
│                   LLM 生成回复                               │
│  输入: 融合后的知识 + 用户 query + system prompt              │
│  约束: 必须引用来源、不得自行诊断、不得推荐处方药              │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
┌──────────────────────────▼──────────────────────────────────┐
│                   safety_gate (最终检查)                      │
│  L1 规则二次验证 + PII 泄露检查 + 边界检查                    │
└──────────────────────────┬──────────────────────────────────┘
                           ↓
                     输出给用户
```

### 6.2 路由策略详解

| 意图类型 | 查询层级 | 路由逻辑 |
|---------|---------|---------|
| 紧急症状咨询 | L1 → L5(病史) → L3 | L1 优先判断，命中红旗直接返回就医建议 |
| 疫苗相关 | L2 → L5(接种记录) | 精确查表 + 个性化计算 |
| 生长发育 | L2(曲线) → L5(记录) | 精确计算百分位 |
| 喂养/辅食 | L1(禁忌) → L2(月龄) → L3(食谱) → L5(过敏) | 多层联合 |
| 睡眠咨询 | L5(睡眠记录) → L3(睡眠知识) → L4(经验) | 数据分析 + 知识辅助 |
| 育儿闲聊 | L4(经验) → L3(百科) → L6(记忆) | 低风险，LLM 主导 |
| 产品使用 | L4(使用指南) | 精确匹配 |
| 记录操作 | L5(写入) | Tool 调用 |

### 6.3 级联与短路

```
规则优先级: L1 > L2 > L5(个性化过滤) > L3 > L4 > L6

短路条件:
  - L1 命中红旗 → 短路，直接返回就医建议
  - L2 精确命中 → 短路，不再查 L3/L4
  - L1 命中禁忌 → 从 L3/L4 结果中过滤掉违禁内容
```

## 7. 来源可信度与版权/许可边界

### 7.1 可信度分级

| 等级 | 来源类型 | 知识层 | 使用约束 |
|------|---------|--------|---------|
| T1 | 国家标准/WHO 发布 | L1, L2 | 可直接作为判断依据 |
| T2 | 权威学术指南（AAP, 中华医学会）| L2, L3 | 可引用，标注来源 |
| T3 | 自建编辑内容 | L3 | 需经医学审核 |
| T4 | 精选社区经验 | L4 | 必须标注"非专业建议" |
| T5 | 用户自报数据 | L5 | 仅用于个性化，不用于医学判断 |

### 7.2 版权/许可边界

| 场景 | 策略 | 说明 |
|------|------|------|
| WHO/CDC 公开数据 | ✅ 可用 | 公共领域数据，注明来源 |
| AAP 指南原文 | ❌ 不可全文引用 | 需获取许可或仅引用摘要/结论 |
| 教科书内容 | ❌ 不可直接复制 | 需获取授权或重新编写 |
| 自建内容 | ✅ 完全可控 | 首选方式 |
| 用户投稿 | ✅ 需用户授权 | 投稿协议中明确许可范围 |
| 网络抓取 | ❌ 禁止 | 版权和质量均不可控 |

### 7.3 推荐策略

> **首选自建内容**：由专业编辑团队基于权威指南重新编写，避免版权风险。  
> **引用而非复制**：对权威来源，仅引用结论/建议，附原文链接。  
> **逐步建设**：MVP 阶段以自建 + 公共领域数据为主，后续按需获取授权。

## 8. 隐私与多成员权限边界

### 8.1 数据分级

| 级别 | 数据类型 | 存储要求 | 传输要求 |
|------|---------|---------|---------|
| 🔴 高敏感 | 姓名、出生日期、疾病史、疫苗记录 | AES-256 加密存储 | TLS 1.3 |
| 🟡 中敏感 | 生长数据、喂养记录 | 加密存储 | TLS 1.3 |
| 🟢 低敏感 | 偏好设置、对话记忆 | 标准存储 | TLS 1.3 |

### 8.2 多成员 RBAC 模型

```
┌─────────────────────────────────┐
│          家庭 (Family)           │
│  family_id: uuid                │
│  created_by: user_id (管理员)    │
├─────────────────────────────────┤
│  成员角色:                       │
│  ┌──────────┬──────────────────┐│
│  │ 管理员    │ 全部读写 + 成员管理││
│  │ (家长)   │ + 数据导出/删除  ││
│  ├──────────┼──────────────────┤│
│  │ 协助看护  │ 日常记录读写     ││
│  │ (祖辈等) │ 不可改基本信息   ││
│  ├──────────┼──────────────────┤│
│  │ 只读成员  │ 查看日常记录     ││
│  │          │ 不可写入         ││
│  ├──────────┼──────────────────┤│
│  │ 临时访客  │ 限时查看指定内容  ││
│  │ (医生等) │ 自动过期         ││
│  └──────────┴──────────────────┘│
└─────────────────────────────────┘
```

### 8.3 权限执行要点

1. **查询隔离**：所有 L5/L6 查询必须带 `family_id` 条件，ORM 层强制注入。
2. **跨家庭禁止**：Agent 不得在单次请求中访问多个家庭的数据。
3. **审计日志**：所有 L5 写操作记录 `who, when, what, from_where`。
4. **数据删除权**：管理员可删除全部家庭数据；成员可删除自己的对话记忆。
5. **LLM 不直接接触 PII**：L5 高敏感字段通过 Tool 接口访问，仅返回必要信息。
6. **对话中的 PII 检测**：LLM 输出经 PII 检测器扫描，防止意外泄露其他家庭信息。

### 8.4 儿童隐私特殊要求

| 要求 | 实现方式 |
|------|---------|
| 最小化收集 | 仅收集功能必需字段，姓名可用昵称替代 |
| 家长同意 | 注册时获取明确授权，可随时撤回 |
| 数据导出 | 支持一键导出全部个人数据 |
| 数据删除 | 支持一键删除，30 天内从备份中彻底清除 |
| 不用于营销 | 儿童数据不得用于广告、推荐等商业目的 |
| 不训练模型 | 用户个人数据不得用于训练 LLM |

## 9. 与数据库 Schema / Eval Harness 的接口约束

### 9.1 对 D1（数据库草案）的约束

| 知识层 | 数据库要求 | Schema 建议 |
|--------|----------|-------------|
| L1 | 代码配置，不入数据库 | — |
| L2 | PostgreSQL 结构化表 | `vaccine_schedule`, `growth_standards`, `milestone_checklist`, `disease_cards`, `drug_reference` |
| L3 | 向量数据库 + 元数据表 | `kb_documents(id, title, source, layer, status, embedding_model_version)` + `kb_chunks(id, doc_id, content, embedding, chunk_index)` |
| L4 | 与 L3 共用，metadata 区分 | 同上，`layer = 'L4'` |
| L5 | PostgreSQL 核心业务表 | `families`, `babies`, `family_members`, `feeding_records`, `sleep_records`, `growth_records`, `vaccination_records`, `allergy_records`, `user_preferences` |
| L6 | Redis + PostgreSQL | Redis: `session:{session_id}:messages`; PG: `conversation_summaries`, `extracted_preferences` |
| 审计 | PostgreSQL | `audit_logs(id, family_id, user_id, action, target_table, target_id, old_value, new_value, timestamp, ip)` |

### 9.2 对 E1（Eval Harness）的约束

| 测试类别 | 覆盖层级 | 测试要求 |
|---------|---------|---------|
| 红旗症状召回率 | L1 | recall ≥ 99.5%，每条规则至少 3 个测试用例 |
| 疫苗计算正确性 | L2 + L5 | 全日历覆盖 + 边界条件（早产儿、延迟接种）|
| RAG 检索质量 | L3 + L4 | MRR@5 ≥ 0.7，precision@3 ≥ 0.8 |
| 回复安全性 | safety_gate | 100% 拦截禁忌建议 |
| 权限隔离 | L5 + L6 | 跨家庭访问测试 → 100% 拦截 |
| 记忆连贯性 | L6 | 跨会话回忆准确率 ≥ 95% |
| 端到端回复质量 | 全层 | 人工评估 + LLM-as-judge |

### 9.3 对 F1（安全合规）的约束

- L5 加密方案需在 F1 中细化（密钥管理、轮换策略）。
- 审计日志格式需在 F1 中标准化。
- PII 检测规则需在 F1 中定义。
- 数据保留策略需在 F1 中与法律顾问确认。

### 9.4 对 G1（Roadmap）的约束

| MVP 阶段 | 需要的知识层 |
|---------|-------------|
| Phase 1（核心记录）| L1(基础红旗), L2(疫苗+生长曲线), L5(核心记录), L6(基础记忆) |
| Phase 2（智能问答）| + L3(自建百科 ≥ 200 篇) |
| Phase 3（社区+个性化）| + L4(经验知识), L6(长期记忆增强) |

## 10. Trade-off 与不推荐方案

### 10.1 方案比较

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **A. 6 层分离（推荐）** | 职责清晰、风险隔离、独立演进 | 系统复杂度较高 | ✅ 推荐 |
| B. 3 层简化（规则/RAG/个性化）| 实现简单 | L2/L3 混合导致检索策略难优化；L5/L6 混合导致隐私管控粒度不足 | ❌ |
| C. 全 RAG | 架构统一 | 医学规则可靠性不可接受；向量检索对精确查表场景低效 | ❌ |
| D. 全 LLM 内置知识 | 最简单 | 不可审计、不可更新、幻觉风险高、无法个性化 | ❌ |
| E. 知识图谱统一 | 关系推理强 | 建设成本极高、育儿场景关系复杂度有限不值得 | ❌ |

### 10.2 关键 Trade-off

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 向量数据库选型 | pgvector（MVP）→ Qdrant（规模化）| MVP 阶段减少组件数量，pgvector 与 L2/L5 共用 PG 实例 |
| Embedding 模型 | 自托管（如 BGE-M3）| 隐私要求不允许将用户 query 发送至第三方 Embedding API |
| L3/L4 是否合并 | 不合并，metadata 区分 | 物理存储可共用，逻辑分离保留检索权重差异化能力 |
| L6 短期记忆引擎 | Redis | 低延迟、自动过期、与持久化分离 |
| 规则引擎实现 | 自建轻量引擎（非 Drools）| 规则量 ~500 条，复杂规则引擎引入过多依赖 |

### 10.3 不推荐做法

| 做法 | 风险 | 替代方案 |
|------|------|---------|
| LLM 直接判断红旗症状 | 漏判可能危及生命 | L1 确定性规则 |
| 将用户数据用于 RAG 索引 | 跨家庭数据泄露 | L5 严格隔离 |
| 使用第三方 Embedding API | 用户 query 隐私泄露 | 自托管模型 |
| 自动从互联网抓取知识 | 版权 + 质量不可控 | 人工审核入库 |
| LLM 自主修改 L1/L2 | 安全性不可保证 | 人工审核 + CI/CD |
| 存储用户对话原文超过 90 天 | 隐私风险 | 摘要化 + 定期清理 |

```
必须:
  ✅ L1: 基础红旗症状规则 (~100 条核心规则)
  ✅ L2: NIP 疫苗日历 + WHO 生长曲线
  ✅ L5: 宝宝档案 + 喂养/睡眠/生长记录 + 单角色权限
  ✅ L6: 单会话上下文（Redis）
  ✅ safety_gate: 基础版
  ✅ 审计日志: 基础版

延后:
  ⏳ L3: 自建百科（Phase 2）
  ⏳ L4: 经验知识（Phase 3）
  ⏳ L6: 跨会话记忆（Phase 2）
  ⏳ 多成员 RBAC（Phase 2）
  ⏳ 数据导出/删除（Phase 2）
```

## 13. 结论

本设计提出 6 层知识架构（L1 硬编码规则 → L2 结构化医学 → L3 育儿百科 → L4 经验知识 → L5 家庭档案 → L6 对话记忆），核心结论如下：

1. **安全层（L1+L2）与智能层（L3+L4）严格分离**：确保医学判断的确定性和可审计性，同时保留 LLM 在自然语言交互上的优势。

2. **公共知识（L1–L4）与私有数据（L5–L6）严格隔离**：满足儿童隐私保护的合规要求，支撑多成员 RBAC 和数据生命周期管理。

3. **"规则优先、向量兜底"的级联检索策略**：高风险场景走确定性路径，低风险场景走 RAG 路径，safety_gate 作为最终守门人。

4. **MVP 可落地**：Phase 1 仅需 L1+L2+L5+L6(基础)，技术栈精简为 PostgreSQL + Redis + 自建规则引擎，8 周内可交付核心功能。

5. **可扩展**：每层独立演进，Phase 2/3 逐步引入 RAG、多成员协作、长期记忆等能力。

本文档直接支撑后续交付物：D1 将基于 §9.1 设计数据库 schema；E1 将基于 §9.2 构建测试用例；F1 将基于 §8 细化合规方案；G1 将基于 §11 规划里程碑。
