## 1 执行摘要

本文档不是新增架构方案，而是把前序 11 份已 PASS 研究件中**尚未最终拍板**、但会影响宝宝专属 agent 落地节奏与风险边界的事项，收敛成一份**决策治理清单**。

目标有三点：

1. 把真正会阻塞 MVP 的问题与可后置的问题分开；
2. 为每个问题给出 trade-off、推荐默认选项、决策 owner 与决策时点；
3. 对医学、法律、许可、地区差异与阈值类事项保持保守：**能标注待人工复核，就不硬编。**

### 1.1 当前已确定的共识（不在 G2 重新争论）

- 产品定位：**育儿记录与信息辅助工具，不是诊断系统，不替代医生。**（F1）
- 高风险医疗场景默认保守升级；红旗症状、急救提示、发布门禁不能交给 LLM 裁决。（C2/F1/E1）
- deterministic rules 负责：生长计算、疫苗排程与状态、RBAC、删除/导出授权、safety_gate、release gate。（A2/C1/C2/F1/E1）
- LLM 负责：自然语言理解、结构化提取、解释、摘要、问答表达；**不做高风险终态决策**。（A2/F1/G1）
- MVP 范围：**单宝宝、单家庭、中国大陆默认、简体中文、文本优先**；多宝宝、多地区、多模态后置。（G1）
- 高风险多模态结果只能进入 candidate/annotation 层，不能直接污染正式医疗或结构化真相源。（D2）

### 1.2 决策优先级分层

| 层级 | 含义 | 处理原则 |
|---|---|---|
| P0 | MVP 前必须敲定，否则阻塞实现/评测/合规 | 本周内定 owner 与默认选项 |
| P1 | MVP 后 30–90 天内需敲定，影响下一阶段扩展 | 可以先按保守默认推进 |
| P2 | 可延后或仅做架构预留 | 不进入 MVP 门禁 |

## 2 本文档如何使用

### 2.1 字段定义

每个决策项统一包含以下字段：

- **问题**：到底要决定什么；
- **为何重要**：不决定会造成什么后果；
- **主要选项 / trade-off**：至少两个可选方向；
- **推荐默认**：当前最保守、最可落地的建议；
- **决策 owner**：谁拍板；
- **决策时点 / 阶段**：什么时候必须定；
- **阻塞影响**：不定会卡住哪些工作；
- **证据来源**：来自哪些已 PASS 文档；
- **人工复核**：是否必须由医学/法务/安全等角色确认。

### 2.2 使用规则

1. 本文档的**推荐默认**，只代表当前研究结论，不等于最终上线配置。  
2. 凡标记 `待人工复核` / `待二次验证` 的内容，**不得直接硬编码为最终事实**。  
3. 若后续决策与 A2/C1/C2/D2/F1/G1 已 PASS 结论冲突，必须回到对应 owner 做增量 review，而不是绕过既有边界。

## 5 P2：可延后但需预留的决策

### 5.1 多地区扩展顺序

**问题：** 中国大陆之后先扩到哪里？  
**trade-off：** 地区越多，本地化医学规则、疫苗程序、法律条款、语言适配成本越高。  
**推荐默认：** 先把中国大陆做透，再按“语言/法规/疫苗程序差异最小化”的原则逐区评估，不在 G2 拍脑袋决定第二地区。  
**owner：** 产品负责人 + 法务 + 医学顾问。  
**人工复核：** 需要。  

### 5.2 多宝宝何时进入

**问题：** 单家庭内支持多个宝宝的时点何时合适？  
**trade-off：** 多宝宝能扩大场景覆盖，但会显著增加时间线切换、数据隔离、RBAC 与提醒复杂度。  
**推荐默认：** MVP 后、在单宝宝链路稳定和 RBAC 三级模型明确后再推进。  
**owner：** 产品负责人。  
**人工复核：** 不需要，但需要用户研究。  

### 5.3 图片/语音何时进入正式路线图

**问题：** 多模态在 Phase 3 之前是否需要提前插入？  
**trade-off：** D2 证明多模态价值明显，但高风险识别、OCR/ASR/CV 阈值、第三方许可都未定。  
**推荐默认：** 继续按 G1 执行：文本优先，多模态后置；若提前试点，也只能是“候选 + 人工确认”，不能改写正式真相源。  
**owner：** 产品负责人 + 技术负责人。  
**人工复核：** 需要。  

### 5.4 是否拆分媒体元数据库

**问题：** 媒体规模上来后，是否要把媒体元数据与主业务库拆分？  
**trade-off：** 早拆更利于扩展，但 MVP 过度设计；晚拆则后续迁移成本高。  
**推荐默认：** MVP 不拆，先在 schema 与对象存储边界上预留；只有在媒体量、检索量和审计量证明必要时再拆。  
**owner：** 技术负责人。  
**人工复核：** 不需要，但需容量评估。  

### 5.5 人工复核 SLA 与运营能力

**问题：** 高风险 OCR/ASR/CV 候选、规则更新、法务文案审校的 SLA 怎么定？  
**trade-off：** SLA 太短需要更强运营能力；太长则影响用户体验和规则迭代。  
**推荐默认：** MVP 前只建立最低可执行 SLA，不追求大规模运营效率指标。  
**owner：** 运营负责人 + 产品负责人。  
**人工复核：** 不需要专业结论，但要和资源配置绑定。  

### 5.6 二类疫苗、社区经验库是否纳入

**问题：** 二类疫苗推荐、UGC 社区经验库是否进入近期范围？  
**trade-off：** 这两类都可能提高用户感知价值，但也明显增加医疗合规与内容审核压力。  
**推荐默认：** **近期都不纳入。** 二类疫苗仅保留为未来待评估议题；社区经验库在没有审核体系前不做。  
**owner：** 产品负责人 + 法务 + 医学顾问。  
**人工复核：** 需要。

## 6 Deterministic Rules vs LLM：决策治理总则

### 6.1 不可改变的分工边界

| 领域 | deterministic rules | LLM |
|---|---|---|
| 红旗症状 / 分诊升级 | **唯一裁决层** | 不参与主判定 |
| 疫苗到期 / 逾期 / 状态机 | **唯一裁决层** | 只做解释文案 |
| 生长 z-score / percentile / corrected age | **唯一计算层** | 只做解释 |
| RBAC / 删除 / 导出授权 | **唯一裁决层** | 不参与 |
| 发布门禁 | **唯一裁决层** | 不参与 |
| 多模态高风险结果入库 | 规则 + 人工复核决定 | 只产出 candidate/annotation |
| 用户自然语言理解 | 校验辅助 | **主要负责** |
| 结构化提取 / 摘要 / 说明 | 校验辅助 | **主要负责** |

### 6.2 总体原则

1. **凡是可枚举、可审计、可回放的，都优先做成 deterministic rules。**  
2. **凡是涉及医学风险、权限、删除、发布、安全门禁的，LLM 只能辅助，不能拍板。**  
3. **当规则与 LLM 输出冲突时，规则一票否决。**  
4. **当事实不明确时，不让 LLM“补全真实世界”，而是显式标记待人工复核。**  

---

## 7 推荐结论

1. **G2 的核心价值不是再发明方案，而是把“还没定的事”显式列出来。**  
2. **MVP 前只解决真正阻塞主链路的 P0 问题**：疫苗默认程序、红旗症状最小集、免责声明、隐私边界、发布门禁、脱敏粒度、提醒引擎路径、规则 DSL 下限。  
3. **MVP 后优先解决本地化与扩展能力问题**：中国标准数字化、早产儿规则、检索质量、多成员 RBAC、字段级加密性能、LLM 降级体验。  
4. **多地区、多宝宝、多模态、二类疫苗、社区经验库都不应挤进 MVP。**  
5. **继续坚持“安全先行、规则兜底、LLM 只做理解和表达”的总路线，不因为交付压力临时放松边界。**  

---

## 8 不推荐做法

| 不推荐做法 | 原因 |
|---|---|
| 在 G2 中把医学、法律、许可未确认事项写成“既定事实” | 会制造错误确定性 |
| 为了赶 MVP，把红旗症状或疫苗规则交给 LLM 临时判断 | 违反 A2/C2/F1 边界 |
| 为了扩功能面，把多地区或多模态提前塞进首发 | 会挤压主链路质量和复核资源 |
| 在没有人工审核前纳入二类疫苗推荐或社区经验库 | 合规与错误信息风险过高 |
| 在日志、提示词、Viewer 中直接暴露儿童敏感数据 | 违反 F1 隐私基线 |
| 在 release gate 未冻结前开始“口头上线” | E1 门禁失效，无法复盘 |

## 10 结论

G2 的结论很简单：

- 前序 11 份文档已经把**推荐架构、规则边界、数据模型、安全基线和 MVP 路线图**定得足够清楚；  
- 真正还没定的，不是“要不要做宝宝 agent”，而是**哪些现实世界细节必须在落地前由人拍板**；  
- 因此，G2 应作为**研究收官件 + 决策治理清单**使用，而不是当成新的方案文档反复重做。  

**最终建议：** 以本文档为决策登记册，逐项关闭 P0 问题后再冻结 MVP；P1/P2 保持保守排期，不为追求功能面而削弱 deterministic rules 与人工复核边界。
