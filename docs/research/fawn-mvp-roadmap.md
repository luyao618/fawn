## 1 执行摘要

本路线图为**宝宝专属 Agent**的 MVP 及后续 90 天实施计划。产品定位：**一个面向 0–6 岁婴幼儿家庭的智能记录与辅助决策 Agent**，**不是医疗诊断系统**。

核心策略：

| 维度 | MVP 决策 |
|------|----------|
| 用户范围 | 单宝宝、单家庭 |
| 地区 | 中国大陆（默认） |
| 语言 | 简体中文 |
| 核心功能 | 喂养记录 · 睡眠记录 · 生长曲线 · 疫苗提醒 · 症状初步分诊 · 家庭协作 · 审计与安全门禁 |
| 架构 | 单主 Agent + Temporal 工作流 + 确定性规则引擎 + safety_gate（继承 A2） |
| 高风险策略 | 规则兜底、LLM 不做终态决策、红旗症状强制升级 |

MVP 目标：**以最小可用产品验证核心记录闭环与安全门禁，在首批内测用户（≤100 家庭）中跑通喂养→记录→提醒→生长→分诊的完整链路。**

## 2 MVP 范围

### 2.1 必须做（P0 — MVP 发布门禁）

| # | 功能 | 继承文档 | 说明 |
|---|------|----------|------|
| 1 | 喂养记录（母乳/配方/辅食） | D1 `feeding` 子表 | 支持文本输入；量/时间/类型结构化写入 |
| 2 | 睡眠记录 | D1 `sleep` 子表 | 入睡/醒来时间、时长、质量标签 |
| 3 | 生长曲线 | C1 生长模块、D1 `growth` 子表 | WHO 标准 Z-score 计算（确定性规则）；异常阈值触发提醒 |
| 4 | 疫苗提醒 | C2 疫苗模块 | 中国大陆 NIP 疫苗程序（`待人工复核`：疫苗时间表细节）；到期/逾期提醒 |
| 5 | 症状初步分诊 | C2 分诊模块、F1 安全门禁 | 红旗症状规则表驱动（`待人工复核`：医学规则细表）；命中红旗 → 强制“建议就医”+ 不给替代方案 |
| 6 | safety_gate 安全门禁 | A2、E1、F1 | 所有 Agent 输出经 safety_gate；高风险拦截；免责声明注入 |
| 7 | 基础 RBAC | F1 | 主照护者 / 协作者 两级权限；删除操作仅主照护者 |
| 8 | 统一 timeline_event 写入 | D1 | 所有记录走 timeline_event + 对应子表；幂等写入 + audit log |
| 9 | 免责声明系统 | F1 | 医疗相关输出必带免责声明；分诊结果注明“非诊断意见” |
| 10 | 数据删除/导出能力 | F1、D1 `retention` | 用户可请求删除/导出个人数据；符合最小合规要求 |
| 11 | 基础评测 & 发布门禁 | E1 | golden set 通过率 ≥ 95%；tool-call correctness ≥ 98%；DB correctness 100%；P0 医疗场景 0 误判 |
| 12 | 列级加密 | F1、D1 | 宝宝姓名、生日、健康数据加密存储 |
| 13 | consent 记录 | D1 `consent` 表 | 用户同意条款版本化存储 |

### 2.2 延后做（P1 — 30–60 天内迭代）

| # | 功能 | 延后理由 |
|---|------|----------|
| 1 | 多宝宝支持 | MVP 先验证单宝宝链路完整性 |
| 2 | 家庭成员邀请/管理 | MVP 仅支持主照护者 + 1 协作者手动配置 |
| 3 | 提醒工作流（Temporal） | MVP 用简单定时任务；30 天后切 Temporal 编排 |
| 4 | 图片/语音输入（多模态） | 高风险 OCR/ASR 结果需人工复核机制，MVP 先文本 |
| 5 | 知识库 L3（循证文章索引）、L4（社区经验库） | B1 已规划后置 |
| 6 | 个性化喂养/睡眠建议 | 需积累足够数据后才有意义 |
| 7 | 多地区疫苗程序 | 各地区疫苗程序差异大（`待人工复核`），先做中国大陆 |

### 2.3 明确不做（P2 — 90 天后或不做）

| # | 功能 | 不做理由 |
|---|------|----------|
| 1 | 医疗诊断 / 处方建议 | **产品不是诊断系统**（F1 红线） |
| 2 | 自动写入高风险医疗记录 | 高风险多模态结果默认候选/待人工确认（C1/C2/D2） |
| 3 | 社区/社交功能 | 不在 Agent 核心价值链 |
| 4 | 第三方设备对接（智能体温计等） | 依赖外部 API 稳定性，风险不可控 |
| 5 | LLM 自主决定删除用户数据 | 删除操作必须人工确认（F1） |
| 6 | LLM 自主调整 RBAC 权限 | 权限变更必须人工确认（F1） |
| 7 | LLM 自主判断发布门禁通过 | 发布门禁为确定性脚本（E1） |

## 3 阶段路线图

### Phase 0：基础设施与规则引擎（第 1–2 周）

**目标：** 搭建可运行的 Agent 骨架、数据库、规则引擎与安全门禁。

| 工程线 | 交付物 | 验收标准 |
|--------|--------|----------|
| 后端 | 单主 Agent 骨架（A2 架构落地） | Agent 可接收文本输入、路由到 tool |
| 数据 | D1 全部表结构建表 + 列级加密 | migration 脚本可重复执行；加密字段验证 |
| 规则引擎 | 红旗症状规则表 v1（`待人工复核`） | ≥ 20 条核心红旗规则上线 |
| 规则引擎 | WHO 生长曲线 Z-score 计算 | 与 WHO 标准数据对齐误差 < 0.01 |
| 规则引擎 | 中国大陆 NIP 疫苗程序表（`待人工复核`） | 覆盖 0–6 岁全部一类疫苗 |
| 安全 | safety_gate 中间件 | 可拦截测试用例中的高风险输出 |
| 安全 | 免责声明注入 | 医疗相关输出 100% 带免责声明 |
| 评测 | golden set v1（≥ 50 条） | 覆盖 P0 场景 |

**依赖：**
- 医学规则细表需医学顾问审核（`待人工复核`）
- 疫苗程序需对照最新版《国家免疫规划疫苗儿童免疫程序》（`待人工复核`）

**风险：**
- 医学规则审核延迟可能阻塞 Phase 1

---

### Phase 1：核心记录闭环（第 3–4 周 — MVP 发布）

**目标：** 内测版发布，≤100 家庭可完成喂养→记录→查看→生长→提醒的完整闭环。

| 工程线 | 交付物 | 验收标准 |
|--------|--------|----------|
| 前端 | 对话式记录界面（喂养/睡眠/生长） | 用户可通过自然语言完成记录 |
| 前端 | 生长曲线可视化 | WHO 标准曲线 + 宝宝数据点 |
| 前端 | 疫苗日历 | 显示已接种/待接种/逾期 |
| 后端 | 喂养/睡眠/生长/疫苗 tool 实现 | tool-call correctness ≥ 98% |
| 后端 | timeline_event 统一写入 + 幂等保证 | 重复请求不产生重复记录 |
| 后端 | 基础 RBAC（主照护者/协作者） | 协作者不可删除；权限隔离测试通过 |
| 后端 | 数据删除/导出 API | 用户可导出 JSON；可请求删除 |
| 规则引擎 | 症状初步分诊 v1 | 红旗命中 → 强制“建议就医”；golden set P0 通过率 100% |
| 安全 | consent 流程 | 首次使用必须同意条款 |
| 安全 | audit log 全覆盖 | 每次写入/删除有 audit 记录 |
| 评测 | 发布门禁全部通过（见第 7 节） | 自动化脚本执行，人工不可绕过 |

**依赖：**
- Phase 0 全部交付
- 前端框架选型确定

**风险：**
- 自然语言→结构化提取准确率不足：用 LLM 提取 + 规则校验双重保障
- 内测用户招募不足：提前准备种子用户池

---

### Phase 2：提醒工作流与家庭协作（第 5–8 周 / 30 天迭代）

**目标：** 引入 Temporal 工作流驱动的智能提醒；增强家庭协作能力。

| 工程线 | 交付物 | 验收标准 |
|--------|--------|----------|
| 后端/工作流 | Temporal 工作流接入（A2） | 疫苗提醒、喂养间隔提醒走 Temporal 编排 |
| 后端 | 多宝宝支持 | 同一家庭可添加多个宝宝，数据隔离 |
| 后端 | 家庭成员邀请/权限管理 | 邀请链接 + 角色分配 |
| 前端 | 提醒通知（推送/消息） | 疫苗到期提前 7 天提醒 |
| 前端 | 家庭成员视图切换 | 协作者可查看但受限操作 |
| 规则引擎 | 喂养间隔异常检测规则 | 超长未喂养 → 提醒 |
| 规则引擎 | 睡眠模式异常检测规则 | 连续 3 天睡眠时长异常 → 提示 |
| 评测 | golden set v2（≥ 100 条） | 覆盖多宝宝、提醒、协作场景 |
| 评测 | workflow eval（E1） | Temporal 工作流回放测试通过 |

**依赖：**
- Temporal 基础设施部署
- 推送通道接入（如微信模板消息、APP 推送）

**风险：**
- Temporal 运维复杂度：建议使用 Temporal Cloud 或由运维团队专项支持
- 推送通道审核周期不可控

---

### Phase 3：多模态输入与知识增强（第 9–12 周 / 60–90 天迭代）

**目标：** 谨慎引入图片/语音输入；扩充知识库；为多地区做准备。

| 工程线 | 交付物 | 验收标准 |
|--------|--------|----------|
| 后端 | 图片输入 — 生长记录拍照提取（D2） | OCR 结果默认候选，用户确认后写入（`待人工复核`：OCR 阈值） |
| 后端 | 语音输入 — 语音记录转文本 | ASR 结果默认候选，用户确认后写入（`待人工复核`：ASR 阈值与第三方许可） |
| 后端 | 知识库 L3 上线（B1） | 循证育儿文章索引，向量检索可用 |
| 规则引擎 | 个性化喂养/睡眠建议 v1 | 基于已积累数据的统计规则，非 LLM 生成 |
| 后端 | 多地区疫苗程序准备 | 架构支持地区切换；首个扩展地区待定（`待人工复核`：目标地区疫苗程序） |
| 安全 | 多模态安全审计 | OCR/ASR/CV 输出全部有 audit log |
| 评测 | 多模态评测集 | 图片/语音场景 golden set |
| 运营 | 用户反馈闭环机制 | 反馈收集 → 分类 → 排优先级 |

**依赖：**
- 第三方 OCR/ASR 服务选型与许可（`待人工复核`：许可条款与数据合规）
- 知识库内容审核团队就位

**风险：**
- 多模态准确率不足导致用户体验下降：默认候选 + 人工确认兜底
- 多地区疫苗程序差异大：每个地区独立审核，不做自动推断

## 7 Deterministic Rules vs LLM 分工

> **核心原则：确定性规则做决策，LLM 做理解与生成；高风险场景 LLM 绝不做终态决策。**

| 职责 | 确定性规则引擎 | LLM |
|------|----------------|-----|
| 红旗症状判断 | ✅ 规则表驱动，命中即升级 | ❌ 不参与判断 |
| WHO Z-score 计算 | ✅ 精确计算 | ❌ 不参与 |
| 疫苗到期/逾期判断 | ✅ 日期规则 | ❌ 不参与 |
| 喂养间隔异常检测 | ✅ 阈值规则 | ❌ 不参与 |
| RBAC 权限判断 | ✅ 权限矩阵 | ❌ 不参与 |
| 删除/导出操作授权 | ✅ 权限 + 人工确认 | ❌ 不参与 |
| 发布门禁执行 | ✅ 自动化脚本 | ❌ 不参与 |
| safety_gate 拦截 | ✅ 规则 + 关键词 + 分类器 | ❌ 不参与终态 |
| 免责声明注入 | ✅ 模板化注入 | ❌ 不参与 |
| 自然语言理解（意图识别） | ❌ | ✅ 理解用户输入 |
| 结构化信息提取 | 校验层 ✅ | 提取层 ✅ |
| 日常育儿问答 | 知识库检索 ✅ | 答案生成 ✅ |
| 记录摘要/趋势描述 | ❌ | ✅ 生成自然语言描述 |
| 对话管理/多轮交互 | ❌ | ✅ |

## 8 Trade-off 分析

### 8.1 为什么先做单宝宝、单地区、核心记录

| 决策 | 理由 |
|------|------|
| **单宝宝优先** | 多宝宝涉及数据隔离、切换体验、UI 复杂度；单宝宝可验证核心价值链 |
| **单地区（中国大陆）优先** | 疫苗程序、医学术语、法律合规各地区差异大；每增一个地区需独立医学/法律审核（`待人工复核`）；先做一个打通闭环 |
| **核心记录优先** | 喂养/睡眠/生长/疫苗是家长每日高频需求，验证 Agent 对日常记录的价值 |
| **文本输入优先** | 多模态（图片/语音）引入 OCR/ASR 准确率风险与第三方依赖；文本链路可控 |

### 8.2 为什么延后

| 延后项 | 理由 |
|--------|------|
| **多地区** | 每个地区的疫苗程序、医学法规、语言适配是独立工作量（`待人工复核`） |
| **多模态高风险自动写入** | C1/C2/D2 明确：高风险 OCR/ASR/CV 结果默认候选/待人工确认 |
| **社区经验库（L4）** | B1 已规划后置；UGC 内容审核机制未建立 |
| **复杂个性化** | 需数据积累；冷启动阶段个性化效果有限 |

### 8.3 关键 trade-off

| Trade-off | 选择 | 代价 | 收益 |
|-----------|------|------|------|
| 规则优先 vs LLM 优先 | 规则优先 | 规则维护成本高；灵活性低 | 可解释、可审计、安全可控 |
| 保守分诊 vs 全面分诊 | 保守（仅红旗识别） | 覆盖症状有限 | 避免误判风险；符合“非诊断系统”定位 |
| 内测小范围 vs 公开发布 | 内测 ≤100 家庭 | 增长慢 | 收集真实反馈；控制风险暴露面 |
| Temporal 延后 vs 立即接入 | Phase 1 不依赖 Temporal | 提醒能力受限 | 降低 MVP 基础设施复杂度 |

## 11 推荐结论

1. **首发聚焦六大核心**：喂养记录、睡眠记录、生长曲线、疫苗提醒、症状初步分诊、家庭协作 + 审计与安全门禁。这六项覆盖了婴幼儿家庭每日最高频、最刚需的场景。

2. **安全门禁是 MVP 第一优先级**：在产品体验之前，先确保不会因错误建议造成健康风险。safety_gate、红旗症状规则、免责声明在 Phase 0 就必须就位。

3. **规则优先策略**：所有涉及健康判断、权限控制、数据安全的决策由确定性规则驱动。LLM 负责自然语言理解与生成，不做终态决策。

4. **小范围验证、快速迭代**：MVP ≤100 家庭内测，收集真实使用数据后再扩展功能与用户规模。

5. **渐进式复杂度**：从单宝宝→多宝宝、从文本→多模态、从单地区→多地区、从固定规则→个性化——每一步扩展都伴随对应的评测集和门禁扩展。

## 12 不推荐做法

| # | 不推荐 | 理由 |
|---|--------|------|
| 1 | MVP 就上多模态自动写入 | OCR/ASR 准确率不足时直接写入会污染核心数据 |
| 2 | LLM 直接输出用药/诊断建议 | 产品不是诊断系统；法律与安全风险不可接受 |
| 3 | 同时启动多地区 | 每个地区的疫苗/法规审核是独立工作量，分散精力 |
| 4 | 用 LLM 做 RBAC 判断 | 权限必须确定性判断，LLM 可能被 prompt injection 绕过 |
| 5 | 用 LLM 决定是否通过发布门禁 | 发布门禁必须是可重复执行的确定性脚本 |
| 6 | 跳过 safety_gate 上线 | 即使“只是内测”也必须有安全门禁 |
| 7 | 一次性构建完整知识库 | 先上 L1/L2 验证检索效果，再逐步扩展 |
| 8 | 在无 golden set 的情况下发布 | E1 明确：无评测集不可发布 |

## 14 结论

宝宝专属 Agent 的 MVP 路线图遵循**“安全先行、规则兜底、小步验证、渐进扩展”**的原则：

1. **Phase 0（第 1–2 周）**：搭建 Agent 骨架、数据库、规则引擎与安全门禁——这是一切的地基。
2. **Phase 1（第 3–4 周）**：发布最小可用内测版，聚焦喂养/睡眠/生长/疫苗/分诊五大核心场景，通过发布门禁后面向 ≤100 家庭开放。
3. **Phase 2（第 5–8 周）**：引入 Temporal 工作流驱动的智能提醒，支持多宝宝与家庭协作。
4. **Phase 3（第 9–12 周）**：谨慎引入多模态输入，扩充知识库，为多地区扩展做架构准备。

所有高风险决策（医疗判断、权限控制、数据删除、发布审批）由确定性规则和人工流程把控，**LLM 不做终态决策**。所有涉及医学、法律、第三方许可的内容显式标注`待人工复核`，确保不因 AI 自信而引入不可控风险。

本路线图继承 A2/B1/C1/C2/D1/D2/E1/F1 全部已 PASS 结论，不新增冲突设计，不改变已确定的架构与安全边界。
